# Module 02 — Basic Searching

## 1. Module Overview

### Objective

Learn how to perform basic searches in Splunk using Search Processing Language (SPL), filter events, work with time ranges, understand event structure, and retrieve relevant information for SOC investigations.

### Learning Outcomes

By the end of this module, you should be able to:

- Understand Splunk Search and SPL.
- Search events from a particular index.
- Perform keyword-based searches.
- Perform field-based searches.
- Use quotation marks to search for phrases.
- Filter events using host, source, and sourcetype.
- Use the Time Range Picker.
- Apply `earliest` and `latest` time modifiers.
- Understand important default event fields.
- Investigate Linux, Windows, firewall, WAP, and infrastructure events.
- Troubleshoot searches returning zero events.

## 2. What Is Splunk Search?

Splunk Search is used to retrieve, filter, and investigate data stored in Splunk indexes.

A SOC Analyst uses Splunk Search to:

- Investigate security alerts.
- Identify failed authentication attempts.
- Investigate suspicious IP addresses.
- Review firewall activities.
- Analyze system and application logs.
- Understand infrastructure availability issues.
- Build evidence and timelines during incident investigations.

### What Is SPL?

SPL stands for **Search Processing Language**.

It is the language used to search, filter, analyze, and transform data in Splunk.

Example:

```spl
index=linux_auth "Failed password"
```

This search retrieves events from the `linux_auth` index containing the phrase `Failed password`.

## 3. Understanding Indexes

An index is a logical storage location in Splunk where indexed events are organized.

When performing an investigation, we should identify the correct index before searching.

### Example Indexes

| Index              | Expected Data                         |
| ------------------ | ------------------------------------- |
| `linux_auth`       | Linux authentication logs             |
| `windows_security` | Windows security events               |
| `firewall`         | Firewall logs                         |
| `network`          | Network device logs                   |
| `wap`              | Wireless access point logs            |
| `iptv`             | IPTV application logs                 |
| `satellite`        | Satellite modem and connectivity logs |
| `_internal`        | Internal Splunk platform logs         |

**Important:** These are example index names. Actual indexes depend on the Splunk environment and its configuration.

### Example 1 — Search an Index

```spl
index=linux_auth
```

Retrieves events stored in the `linux_auth` index.

### Example 2 — Search Splunk Internal Events

```spl
index=_internal
```

Retrieves internal events generated by Splunk itself.

### Example 3 — Search Error Events

```spl
index=_internal error
```

Retrieves internal events matching the keyword `error`.

## 4. Keyword-Based Searching

A keyword search retrieves events containing a particular word or phrase.

### Example 1 — Search a Keyword

```spl
index=_internal error
```

Searches internal Splunk events containing the keyword `error`.

### Example 2 — Search Another Keyword

```spl
index=_internal warning
```

Searches internal events containing `warning`.

### Example 3 — Search an Exact Phrase

```spl
index=linux_auth "Failed password"
```

Searches for the phrase `Failed password`.

### Why Do We Use Quotation Marks?

Quotation marks tell Splunk to search for a phrase rather than treating the words as separate search terms.

Example:

```spl
index=linux_auth "Failed password"
```

The phrase is searched together.

Without quotation marks:

```spl
index=linux_auth Failed password
```

Splunk treats the words as separate search terms rather than one exact phrase.

### Difference Between Keyword and Field-Based Searches

| Keyword-Based Search                           | Field-Based Search                        |
| ---------------------------------------------- | ----------------------------------------- |
| Searches for a word or phrase in event content | Searches using a field name and its value |
| Does not require specifying a field            | Requires a field and value                |
| Example: `Password`                            | Example: `user="admin"`                   |

Example:

```spl
index=linux_auth Password
```

Searches for the keyword `Password`.

```spl
index=linux_auth user="admin"
```

Searches for events where the `user` field has the value `admin`.

Remember:

- `user` is the field name.
- `admin` is the field value.

**Important:** Field-based searches require the relevant field to be available or extracted in the events.

## 5. Using Fields in Basic Searches

Fields help identify and filter specific information within events.

### Common Fields

| Field        | Description                                      |
| ------------ | ------------------------------------------------ |
| `host`       | Host or system associated with the event         |
| `source`     | Origin of the event                              |
| `sourcetype` | Type or format of the event data                 |
| `index`      | Index containing the event                       |
| `user`       | Username, when available                         |
| `src_ip`     | Source IP address, when extracted                |
| `dest_ip`    | Destination IP address, when extracted           |
| `action`     | Action associated with the event, when available |

### Example 1 — Filter by Host

```spl
index=linux_auth host="server01"
```

Searches Linux authentication events associated with `server01`.

### Example 2 — Filter by Sourcetype

```spl
index=linux_auth sourcetype=linux_secure
```

Searches events with the specified sourcetype.

### Example 3 — Filter by Source

```spl
index=linux_auth source="/var/log/auth.log"
```

Searches events from the specified source.

**Note:** These source and sourcetype examples depend on how the environment collects and labels Linux logs.

## 6. Time Range Picker

The Time Range Picker controls the time period for which Splunk retrieves events.

It helps analysts narrow investigations to relevant periods.

### Common Time Ranges

- All time
- Last 15 minutes
- Last 60 minutes
- Last 4 hours
- Last 24 hours
- Last 7 days
- Last 30 days
- Custom time range

### Example

Suppose an alert was generated around 10:00 AM.

Instead of searching all available events, select a relevant period around 10:00 AM.

This reduces unnecessary search results and helps the analyst focus on the incident.

### Why Is the Time Range Important?

An event may exist in Splunk but not appear because the selected time range excludes it.

Therefore, always verify the time range before concluding that an event does not exist.

## 7. Using earliest and latest Time Modifiers

Splunk supports time modifiers directly in SPL.

The two important modifiers are:

| Modifier   | Meaning                             |
| ---------- | ----------------------------------- |
| `earliest` | Beginning of the search time window |
| `latest`   | End of the search time window       |

### Example 1 — Search the Last 24 Hours

```spl
index=linux_auth earliest=-24h latest=now
```

Searches from 24 hours ago until the current time.

### Example 2 — Search from Today's Midnight

```spl
index=linux_auth earliest=@d latest=now
```

Searches from midnight at the beginning of the current day until now.

### Example 3 — Search the Previous Seven Complete Days

```spl
index=linux_auth earliest=-7d@d latest=@d
```

Searches from midnight seven days ago until midnight today.

### Common Relative Time Units

| Modifier | Meaning               |
| -------- | --------------------- |
| `s`      | Seconds               |
| `m`      | Minutes               |
| `h`      | Hours                 |
| `d`      | Days                  |
| `w`      | Weeks                 |
| `mon`    | Months                |
| `y`      | Years                 |
| `@d`     | Beginning of the day  |
| `@h`     | Beginning of the hour |
| `@w`     | Beginning of the week |

### Combining Time Modifiers with Search

Example:

```spl
index=linux_auth earliest=-3h latest=now
```

Searches Linux authentication events from the last three hours.

Example:

```spl
index=linux_auth earliest=-1h latest=now "Failed password"
```

Searches for failed password events in the last hour.

### Time Range Picker vs. Explicit Time Modifiers

When explicit `earliest` and `latest` modifiers are included in SPL, they override the Time Range Picker's time window.

Example:

```spl
index=linux_auth earliest=-24h latest=now
```

Even if the Time Range Picker is set to Last 15 minutes, this search uses the explicit 24-hour time window.

## 8. Understanding Splunk Event Structure

An event represents an individual record of information stored in Splunk.

Example Linux authentication event:

```text
Nov 19 08:10:15 server01 sshd[1234]: Failed password for admin from 192.168.1.50
```

Splunk maintains important metadata fields associated with events.

### Important Default Fields

| Field        | Description                        |
| ------------ | ---------------------------------- |
| `_time`      | Timestamp assigned to the event    |
| `_raw`       | Original raw event data            |
| `_indextime` | Time when Splunk indexed the event |
| `host`       | Host associated with the event     |
| `source`     | Origin of the event                |
| `sourcetype` | Format or type of the event        |
| `index`      | Index containing the event         |

### 8.1 `_time`

Represents the event timestamp assigned by Splunk.

Example:

```text
_time = 2026-11-19 08:10:15
```

This is the timestamp used when searching and displaying events.

It may represent the original event timestamp rather than the exact time the event arrived in Splunk.

### 8.2 `_raw`

Contains the original raw event data.

Example:

```text
Nov 19 08:10:15 server01 sshd[1234]: Failed password for admin from 192.168.1.50
```

The original event message is available in `_raw`.

### 8.3 `_indextime`

Represents the time Splunk indexed an event.

Example:

| Field        | Time     |
| ------------ | -------- |
| `_time`      | 08:00 AM |
| `_indextime` | 08:10 AM |

This means the event was indexed approximately 10 minutes after its event timestamp.

This is useful when investigating ingestion delays.

### 8.4 `host`

Identifies the host associated with the event.

Examples:

```text
host=server01
host=192.168.1.10
host=ip-10-48-129-150
```

The value can be a hostname, IP address, or another configured host identifier.

Do not assume that the host field always contains an IP address.

### 8.5 `source`

Identifies where the event originated.

Example:

```text
source=/var/log/auth.log
```

The source can be a file path or another input/data origin.

### 8.6 `sourcetype`

Identifies the type or format of the event data.

Example:

```text
sourcetype=linux_secure
```

### Difference Between Source and Sourcetype

| Source                       | Sourcetype                         |
| ---------------------------- | ---------------------------------- |
| Identifies the data origin   | Identifies the data format or type |
| Example: `/var/log/auth.log` | Example: `linux_secure`            |

Remember:

- Source tells us where the data came from.
- Sourcetype tells us what kind of data format Splunk is dealing with.

## 9. Basic SOC Searches

The same searching concepts can be applied to security monitoring and infrastructure monitoring.

### 9.1 Linux Authentication Monitoring

Search failed SSH authentication attempts:

```spl
index=linux_auth "Failed password"
```

Search failed password attempts on a particular server:

```spl
index=linux_auth host="server01" "Failed password"
```

Investigate a particular username:

```spl
index=linux_auth user="admin"
```

The actual index, sourcetype, message format, and extracted fields depend on the Linux log collection configuration.

### 9.2 Windows Security Monitoring

Search Windows Security events:

```spl
index=windows_security
```

Search for failed authentication events using a known event message:

```spl
index=windows_security "failed"
```

### 9.3 Firewall Monitoring

Search firewall events:

```spl
index=firewall
```

Search for denied traffic:

```spl
index=firewall deny
```

A firewall deny event indicates that traffic was denied. It does not prove that an earlier connection had been successfully established.

### 9.4 Wireless Access Point Monitoring

Search WAP authentication failures:

```spl
index=wap "authentication failed"
```

Search events from a particular WAP:

```spl
index=wap host="WAP-01"
```

The objective is to investigate repeated authentication failures, affected devices, and possible connectivity or security issues.

### 9.5 Satellite Connectivity Monitoring

Search satellite modem events:

```spl
index=satellite
```

Search for link-related failures:

```spl
index=satellite down
```

The objective is to understand link availability and identify relevant operational events.

### 9.6 IPTV Monitoring

Search IPTV events:

```spl
index=iptv
```

Search token-related events:

```spl
index=iptv token
```

Token failures may be caused by session expiry, authentication problems, application issues, or suspicious activity. Investigate the surrounding evidence before concluding the root cause.

**Note:** The above indexes and keywords are illustrative. Use the actual index names and event messages configured in your Splunk environment.

## 10. Troubleshooting Searches Returning Zero Events

A Splunk search returning zero events does not automatically mean that no activity occurred.

### Possible Reasons

| Reason                 | Explanation                                          |
| ---------------------- | ---------------------------------------------------- |
| Incorrect index        | Searching the wrong index                            |
| Incorrect time range   | Relevant events are outside the selected time period |
| Incorrect keyword      | Search term does not match the actual event          |
| Incorrect sourcetype   | Filtering using the wrong sourcetype                 |
| Incorrect host         | Host filter does not match the indexed host          |
| Data ingestion failure | Logs are not reaching Splunk                         |
| Incorrect source       | Searching the wrong data origin                      |
| Permissions            | User does not have access to the relevant index      |

### Troubleshooting Procedure

When a search returns zero events:

1. Check the selected time range.
2. Verify the index name.
3. Remove additional filters and search the index alone.
4. Check the actual event message and keywords.
5. Verify the host field.
6. Verify the source and sourcetype.
7. Investigate whether data ingestion is working.
8. Check whether the user has permission to access the index.

Example troubleshooting sequence:

```spl
index=linux_auth
```

Then:

```spl
index=linux_auth host="server01"
```

Then:

```spl
index=linux_auth "Failed password"
```

Add filters gradually instead of starting with a complicated search.

## 11. Practical Analysis — Understanding Splunk Internal Logs

During Module 2, three events from the TryHackMe Splunk environment were analyzed.

These examples demonstrate how Splunk records and exposes its own internal activity.

### Event 1 — Splunk REST API Access

Raw event:

```text
127.0.0.1 - splunk-system-user [18/Nov/2026:15:08:17.835 +0000] "GET //services/server/roles?output_mode=json HTTP/1.0" 200 798 "-" "Python-httplib2/0.20.4 (gzip)" - - - 0ms
```

Metadata:

```text
host=ip-10-48-129-150

source=/opt/splunk/var/log/splunk/splunkd_access.log

sourcetype=splunkd_access
```

#### Explanation

| Element                  | Meaning                       |
| ------------------------ | ----------------------------- |
| `127.0.0.1`              | Local loopback address        |
| `splunk-system-user`     | System-associated Splunk user |
| `18/Nov/2026`            | Event date                    |
| `15:08:17.835 +0000`     | Timestamp in UTC              |
| `GET`                    | HTTP GET request              |
| `/services/server/roles` | Splunk REST API endpoint      |
| `output_mode=json`       | Requests JSON output          |
| `200`                    | Successful HTTP response      |
| `798`                    | Response size in bytes        |
| `Python-httplib2`        | HTTP client user agent        |
| `0ms`                    | Reported request duration     |

The `/services/server/roles` endpoint retrieves role information applicable to the Splunk server.

The `127.0.0.1` address is a loopback address. It indicates that the client connection was local to the machine from Splunk's perspective.

It does not indicate an external attacker.

The double slash in `//services` is visible in the event, but the successful response does not establish that the request was malicious or that the extra slash caused an issue.

### Event 2 — Splunk Internal File Processing

Raw event:

```text
11-18-2026 15:08:16.215 +0000 INFO TailReader [1365 tailreader0] - Batch input finished reading file='/opt/splunk/var/spool/splunk/tracker.log'
```

Metadata:

```text
host=ip-10-48-129-150

source=/opt/splunk/var/log/splunk/splunkd.log

sourcetype=splunkd
```

#### Explanation

| Element                             | Meaning                              |
| ----------------------------------- | ------------------------------------ |
| `11-18-2026`                        | Event date                           |
| `15:08:16.215 +0000`                | UTC timestamp                        |
| `INFO`                              | Informational log level              |
| `TailReader`                        | Splunk internal component            |
| `[1365 tailreader0]`                | Process/thread information           |
| `Batch input finished reading file` | Completed reading the specified file |
| `tracker.log`                       | File referenced in the message       |

This is an informational message, not an error.

It indicates that the TailReader component finished reading the file.

It does not independently prove that all expected business data was successfully indexed.

### Event 3 — Splunk Web Search Results Access

The event contains an HTTP GET request made by the Splunk Web interface:

```text
127.0.0.1 - admin [18/Nov/2026:15:08:15.570 +0000] "GET /en-US/splunkd/__raw/servicesNS/nobody/search/search/v2/jobs/1795014494.10/events?output_mode=json&offset=0&count=50 HTTP/1.0" 200 162632
```

Metadata:

```text
host=ip-10-48-129-150

source=/opt/splunk/var/log/splunk/splunkd_ui_access.log

sourcetype=splunkd_ui_access
```

#### Explanation

| Element                               | Meaning                                      |
| ------------------------------------- | -------------------------------------------- |
| `127.0.0.1`                           | Local loopback address                       |
| `admin`                               | Splunk administrator account                 |
| `GET`                                 | HTTP GET request                             |
| `search/v2/jobs/1795014494.10/events` | Search job events endpoint                   |
| `1795014494.10`                       | Search job ID (SID)                          |
| `output_mode=json`                    | Requests JSON output                         |
| `offset=0`                            | Starts from the first result                 |
| `count=50`                            | Requests up to 50 events in this response    |
| `200`                                 | Successful HTTP response                     |
| `162632`                              | Response size in bytes                       |
| `68ms`                                | Request duration shown in the complete event |

The `count=50` parameter does not prove that the search returned exactly 50 events in total. It specifies the requested result count for this response.

The event's user-agent identifies a Chrome browser on Windows. A user-agent string is client-supplied and can be modified, so it is not definitive proof of the actual operating system.

### Difference Between the Three Splunk Log Files

| File                    | Purpose                                                          |
| ----------------------- | ---------------------------------------------------------------- |
| `splunkd_access.log`    | Records HTTP requests served through Splunk's management service |
| `splunkd.log`           | Records internal Splunk daemon activity                          |
| `splunkd_ui_access.log` | Records browser/UI-related requests served by Splunk             |

### Understanding the Timeline

All three events are associated with the same Splunk host.

| Time (UTC)   | Event                                                   |
| ------------ | ------------------------------------------------------- |
| 15:08:15.570 | Administrator browser retrieves search results          |
| 15:08:16.215 | TailReader finishes reading `tracker.log`               |
| 15:08:17.835 | System-associated user requests server role information |

These events occurred within approximately 2.3 seconds.

Their close timestamps do not prove that one event caused another.

### SOC Investigation Perspective

These logs are useful for:

- Monitoring Splunk platform activity.
- Understanding administrator interactions.
- Investigating REST API access.
- Troubleshooting search and indexing behaviour.
- Reviewing Splunk Web activity.
- Investigating unusual internal system requests.

The examples contain successful HTTP responses and loopback client addresses. There is no obvious external attacker address or failed HTTP status in these records.

However, successful HTTP status codes alone do not prove that the activity is benign. An analyst should consider user activity, audit records, expected administrative operations, surrounding events, and configuration changes.

**Key Learning:** These are internal Splunk platform events, not direct evidence of SSH attacks or suspicious activity on an external endpoint.

## 14. Knowledge Assessment — Correct Answers

### Basic Searching

**1. What is a Splunk search?**

Splunk Search is used to retrieve, filter, and investigate events stored in Splunk indexes.

**2. What does SPL stand for?**

SPL stands for Search Processing Language.

**3. What is the purpose of `index=linux_auth`?**

It tells Splunk to retrieve events stored in the `linux_auth` index.

**4. What is the difference between keyword search and field-based search?**

Keyword search searches for words or phrases in event content. Field-based search filters events using field names and their values.

**5. Why do we use quotation marks around `"Failed password"`?**

To search for the phrase `Failed password` rather than treating the words as separate search terms.

### Time Range

**6. What is the purpose of the Time Range Picker?**

It controls the time period for which Splunk retrieves events.

**7. What is the difference between earliest and latest?**

`earliest` specifies the beginning of a search time window, while `latest` specifies its end.

**8. What does `earliest=-24h latest=now` mean?**

It retrieves events from 24 hours ago until the current time.

**9. What does `earliest=@d latest=now` mean?**

It retrieves events from midnight at the beginning of the current day until now.

**10. What happens when explicit time modifiers are used together with the Time Range Picker?**

Explicit `earliest` and `latest` modifiers override the Time Range Picker's time window.

### Event Structure

**11. What is `_time`?**

The timestamp assigned to the event by Splunk.

**12. What is `_raw`?**

The original raw event data.

**13. What is `_indextime`?**

The time Splunk indexed the event.

**14. What is the difference between source and sourcetype?**

Source identifies where the data originated, while sourcetype identifies its format or type.

**15. What information does the host field provide?**

It identifies the host associated with the event, such as a server hostname or configured device identifier.

### Practical SOC Questions

**16. How would you search for failed SSH authentication attempts in a Linux server?**

```spl
index=linux_auth "Failed password"
```

To filter by a particular server:

```spl
index=linux_auth host="server01" "Failed password"
```

**17. Why might a search return zero events?**

Possible reasons include:

- Incorrect time range.
- Wrong index.
- Data ingestion failure.
- Incorrect sourcetype.
- Incorrect host or source.
- Incorrect search keyword.
- Insufficient permissions.

**18. How would you investigate an alert generated three hours ago?**

Start with a search covering the relevant period:

```spl
index=linux_auth earliest=-3h latest=now
```

To isolate the period between three and two hours ago:

```spl
index=linux_auth earliest=-3h latest=-2h
```

For an actual incident, use the alert's exact timestamp and search an appropriate period before and after it.

**19. Why should you verify the index before starting an investigation?**

To ensure that you are searching the correct data collection. Searching the wrong index can produce zero results and may lead to incorrect investigation conclusions.

**20. How would you search for repeated WAP authentication failures?**

```spl
index=wap "authentication failed"
```

To investigate a particular WAP:

```spl
index=wap host="WAP-01" "authentication failed"
```

Identifying repeated failures by username, client or source IP will require additional search commands covered in later modules.
