# Module 01 – Introduction to Splunk: Interview Questions and Answers

## Module Overview

This document contains interview questions and answers covering the basic concepts of Splunk, SIEM, Splunk architecture, data collection, configuration files, ports, metadata, and troubleshooting.

The questions are organized from beginner to scenario-based level to help prepare for SOC Analyst and Splunk-related technical interviews.

---

# Section 1 – Splunk Fundamentals

## Q1. What is Splunk?

**Answer:**

Splunk is a platform used to collect, index, search, monitor, analyze, and visualize machine-generated data.

It can collect data from different sources, including:

- Linux servers.
- Windows servers.
- Firewalls.
- Routers and switches.
- Applications.
- VPN gateways.
- Security tools.
- Cloud platforms.

Splunk helps organizations centrally analyze data and investigate operational or security-related activities.

## Q2. Why do organizations use Splunk?

**Answer:**

Organizations use Splunk to manage and analyze large amounts of machine-generated data.

Common purposes include:

1. Centralized log collection.
2. Infrastructure monitoring.
3. Application monitoring.
4. Security monitoring.
5. Troubleshooting.
6. Incident investigation.
7. Alert generation.
8. Dashboard and report creation.
9. Event correlation.
10. Root-cause analysis.

## Q3. What is machine-generated data?

**Answer:**

Machine-generated data is information automatically produced by systems, applications, operating systems, and network devices.

Examples include:

- Linux authentication logs.
- Windows Security Event Logs.
- Firewall traffic logs.
- Router interface logs.
- VPN connection logs.
- Web server access logs.
- Application error logs.
- Endpoint security alerts.

Splunk can collect this data and make it searchable.

## Q4. What is a log?

**Answer:**

A log is a record generated by a system, application, or device that describes an activity, event, or condition.

Example:

```text
Nov 18 10:15:22 server01 sshd[1234]: Failed password for invalid user admin from 192.168.1.50 port 52341 ssh2
```

This log records a failed SSH authentication attempt.

It contains useful information such as the timestamp, hostname, username, source IP address, and authentication result.

## Q5. What is an event in Splunk?

**Answer:**

An event is an individual record represented and processed by Splunk.

When a log record is ingested and processed by Splunk, it becomes searchable as an event.

For example, an SSH authentication failure recorded in a Linux log file can become an individual searchable event in Splunk.

## Q6. What is the difference between a log and an event?

**Answer:**

A log is a record generated by a system or application. An event is an individual record represented and processed by Splunk.

For example:

- A line in `/var/log/auth.log` is a log record.
- The corresponding record returned by a Splunk search is an event.

In daily SOC operations, these terms are sometimes used interchangeably.

## Q7. What is SIEM?

**Answer:**

SIEM stands for **Security Information and Event Management**.

A SIEM solution collects and analyzes security-related information from different systems to help organizations detect, investigate, and respond to security incidents.

Common SIEM capabilities include:

- Security log collection.
- Event analysis.
- Threat detection.
- Event correlation.
- Alert generation.
- Incident investigation.
- Security reporting.

## Q8. Is Splunk a SIEM tool?

**Answer:**

Splunk is a data platform that provides collection, indexing, searching, monitoring, and analytics capabilities.

Splunk Enterprise is a general-purpose data platform.

Splunk Enterprise Security (ES) is a security-focused solution built on the Splunk platform that provides SIEM capabilities.

Therefore, Splunk Enterprise and Splunk Enterprise Security should not be treated as exactly the same product.

## Q9. What is the difference between Splunk Enterprise and Splunk Enterprise Security?

**Answer:**

| Splunk Enterprise                                 | Splunk Enterprise Security                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------- |
| General-purpose data platform.                    | Security-focused solution built on Splunk.                                      |
| Collects, indexes, searches, and analyzes data.   | Provides security monitoring and investigation capabilities.                    |
| Supports operational and application monitoring.  | Supports security use cases such as threat detection and correlation.           |
| Provides search, dashboards, reports, and alerts. | Adds security-focused workflows, correlation searches, and risk-based alerting. |

# Section 2 – Splunk Architecture

## Q10. What are the main components of Splunk architecture?

**Answer:**

The main components to understand are:

1. Forwarder.
2. Indexer.
3. Search Head.
4. Deployment Server.
5. License Manager.
6. Cluster Manager.

The Forwarder, Indexer, and Search Head are the key components in the basic data flow.

## Q11. What is a Forwarder in Splunk?

**Answer:**

A Forwarder is a Splunk component that collects data from a source system and sends it to another Splunk component.

It is commonly installed on servers to collect operating system and application logs.

Examples:

- Linux servers.
- Windows servers.
- Application servers.
- Virtual machines.

The type of Forwarder and its configuration determine what processing can be performed before forwarding.

## Q12. What is a Universal Forwarder?

**Answer:**

A Universal Forwarder (UF) is a lightweight Splunk agent used to collect and forward data from source systems.

Its responsibilities include:

- Monitoring configured log files.
- Collecting configured event data.
- Forwarding data to receiving Splunk instances.
- Using relatively few system resources.

Example:

A Universal Forwarder monitors:

```text
/var/log/auth.log
```

It sends collected data to a Splunk Indexer.

The Indexer processes and stores the events.

## Q13. What is a Heavy Forwarder?

**Answer:**

A Heavy Forwarder (HF) is a full Splunk Enterprise instance configured to forward data.

It can perform additional processing before forwarding, including:

- Parsing.
- Filtering.
- Routing.
- Transformations.
- Data forwarding.

A Heavy Forwarder generally consumes more system resources than a Universal Forwarder.

## Q14. What is the difference between Universal Forwarder and Heavy Forwarder?

**Answer:**

| Feature               | Universal Forwarder      | Heavy Forwarder                  |
| --------------------- | ------------------------ | -------------------------------- |
| Installation          | Lightweight agent        | Full Splunk Enterprise instance  |
| Resource usage        | Low                      | Higher                           |
| Log collection        | Yes                      | Yes                              |
| Parsing capability    | Limited                  | Full parsing capabilities        |
| Filtering and routing | Limited                  | More advanced capabilities       |
| Splunk Web            | No full search interface | Available                        |
| Common use            | Collect and forward data | Process, route, and forward data |

## Q15. What is an Intermediate Forwarder?

**Answer:**

An Intermediate Forwarder receives data from upstream Forwarders and sends it to downstream Splunk components.

It may be a Universal Forwarder or Heavy Forwarder, depending on the required processing.

Example:

```text
Linux Servers
      |
      v
Universal Forwarders
      |
      v
Intermediate Forwarder
      |
      v
Indexer
```

Organizations may use intermediate Forwarders to centralize data routing and forwarding.

## Q16. What is an Indexer?

**Answer:**

An Indexer is a Splunk component responsible for processing incoming data and storing it in a searchable form.

Its responsibilities include:

- Receiving incoming data.
- Processing events.
- Applying configured metadata and indexing rules.
- Storing indexed events.
- Making data available for searching.

For example, a Linux Indexer may store SSH authentication events such as successful and failed login attempts.

## Q17. What is an index in Splunk?

**Answer:**

An index is a logical storage location in Splunk where indexed events are stored.

Examples:

```text
main
_internal
linux_auth
windows
firewall
network
```

A search such as:

```spl
index=linux_auth
```

retrieves events stored in the `linux_auth` index, subject to the user's permissions and selected time range.

## Q18. What is a Search Head?

**Answer:**

A Search Head provides the search and analysis environment for Splunk users.

Its responsibilities include:

- Executing searches.
- Coordinating searches against Indexers.
- Displaying search results.
- Creating reports.
- Creating dashboards.
- Supporting alerts and search-based workflows.

In a distributed environment, a Search Head can coordinate searches across multiple Indexers.

## Q19. What is Splunk Web?

**Answer:**

Splunk Web is the browser-based user interface used to interact with Splunk.

It allows users to:

- Search data.
- View events.
- Create dashboards.
- Generate reports.
- Manage alerts.
- Access configuration options, depending on permissions.

The default Splunk Web port is TCP 8000.

Example:

```text
http://192.168.56.101:8000
```

## Q20. What is a Deployment Server?

**Answer:**

A Deployment Server centrally manages configuration deployment to supported Splunk Forwarders.

It can distribute:

- Inputs configurations.
- Outputs configurations.
- Application packages.
- Other supported Forwarder configurations.

For example, an administrator can use a Deployment Server to distribute a common log collection configuration to multiple Universal Forwarders.

## Q21. What is a License Manager?

**Answer:**

A License Manager manages Splunk license usage and related license information.

It helps administrators monitor whether their Splunk deployment is operating within its licensing limits.

## Q22. What is a Cluster Manager?

**Answer:**

A Cluster Manager coordinates an Indexer cluster.

It helps manage:

- Cluster configuration.
- Data replication.
- Search-factor requirements.
- Replication-factor requirements.
- Cluster health.

It is mainly relevant to distributed Splunk environments.

# Section 3 – Splunk Data Flow

## Q23. Explain the basic Splunk data flow.

**Answer:**

The basic Splunk data flow is:

```text
Data Source
    |
    v
Forwarder
    |
    v
Indexer
    |
    v
Search Head
    |
    v
Splunk Web
    |
    v
Analyst
```

Explanation:

1. A system generates logs.
2. A Forwarder collects the configured data.
3. The Forwarder sends the data to a receiving Splunk component.
4. The Indexer processes and stores the data.
5. The Search Head coordinates searches.
6. Splunk Web displays search results.
7. The analyst investigates the returned events.

Actual deployments may contain additional components, such as intermediate Forwarders and multiple Indexers.

## Q24. What happens when a Linux server generates an authentication log?

**Answer:**

Consider this example:

```text
Failed password for invalid user admin from 192.168.1.50 port 52341 ssh2
```

The process is:

1. Linux generates the authentication log.
2. A Universal Forwarder monitors the configured authentication log file.
3. The Forwarder sends the data to a receiving Splunk instance.
4. The Indexer processes and stores the event.
5. A SOC Analyst searches for the event using SPL.
6. The analyst reviews the username, source IP, timestamp, and authentication result.
7. The analyst decides whether further investigation is needed.

## Q25. Does a Forwarder store data like an Indexer?

**Answer:**

A Forwarder primarily collects and forwards data. It is not intended to perform the same indexing and searchable storage role as an Indexer.

A Universal Forwarder may maintain internal files and temporary data needed for its operation, but its main purpose is data collection and forwarding.

The Indexer is responsible for indexing and storing events for searching.

## Q26. Can Splunk receive data without a Universal Forwarder?

**Answer:**

Yes.

Splunk supports several data collection methods, including:

- Syslog.
- HTTP Event Collector (HEC).
- Monitor inputs.
- Scripted inputs.
- API integrations.
- Supported Windows Event Log inputs.

A Universal Forwarder is common for server log collection, but it is not mandatory for every data source.

# Section 4 – Data Collection Methods

## Q27. What is Syslog?

**Answer:**

Syslog is a standard protocol used to transmit log messages from devices and applications to a logging server.

Common sources include:

- Firewalls.
- Routers.
- Switches.
- Linux systems.
- Network appliances.

A common architecture is:

```text
Firewall
    |
    v
Syslog Server
    |
    v
Splunk
```

The Syslog server receives messages and can forward them to Splunk.

## Q28. What are the common Syslog ports?

**Answer:**

Commonly used ports are:

| Protocol        | Port |
| --------------- | ---: |
| Syslog over UDP |  514 |
| Syslog over TCP |  514 |
| Syslog over TLS | 6514 |

These are common port assignments and may vary depending on the environment.

## Q29. What is HTTP Event Collector?

**Answer:**

HTTP Event Collector (HEC) is a Splunk feature that allows applications and supported clients to send events to Splunk using HTTP or HTTPS.

HEC commonly uses TCP port 8088.

It uses an authentication token to authorize event submission.

A typical data flow is:

```text
Application
    |
    v
HTTP / HTTPS
    |
    v
Splunk HEC
    |
    v
Splunk Data Processing
```

## Q30. What is the difference between Universal Forwarder, Syslog, and HEC?

**Answer:**

| Method              | Purpose                                                                         |
| ------------------- | ------------------------------------------------------------------------------- |
| Universal Forwarder | Collects data from configured inputs on a machine and forwards it to Splunk.    |
| Syslog              | Transmits log messages from devices and applications to a logging receiver.     |
| HEC                 | Receives event data from applications and supported clients over HTTP or HTTPS. |

The correct method depends on the data source, architecture, and integration requirements.

## Q31. What is API-based data collection?

**Answer:**

Some applications and platforms expose APIs that allow other systems to retrieve information.

Splunk can collect data through supported integrations, add-ons, or custom collection scripts.

For example, a security platform may expose an API containing alert information. A collection process can retrieve those alerts and send them to Splunk.

# Section 5 – Configuration Files

## Q32. What is inputs.conf?

**Answer:**

`inputs.conf` defines what data Splunk should collect and how it should collect it.

It can configure:

- File monitoring.
- Directory monitoring.
- Network inputs.
- Windows Event Log inputs.
- Scripted inputs.
- Other supported input types.

Example:

```ini
[monitor:///var/log/auth.log]
disabled = 0
index = linux_auth
sourcetype = linux_secure
```

In this example:

- The file being monitored is `/var/log/auth.log`.
- The input is enabled.
- The configured index is `linux_auth`.
- The configured sourcetype is `linux_secure`.

## Q33. What is outputs.conf?

**Answer:**

`outputs.conf` defines where a Forwarder sends its data.

Example:

```ini
[tcpout]
defaultGroup = primary_indexer

[tcpout:primary_indexer]
server = 192.168.56.101:9997
```

In this example, the Forwarder sends data to `192.168.56.101` on TCP port `9997`.

## Q34. What is the difference between inputs.conf and outputs.conf?

**Answer:**

| Configuration  | Purpose                                             |
| -------------- | --------------------------------------------------- |
| `inputs.conf`  | Defines what data to collect and how to collect it. |
| `outputs.conf` | Defines where collected data should be sent.        |

Easy way to remember:

- `inputs.conf` = What to collect.
- `outputs.conf` = Where to send.

The receiving Splunk instance must also be configured to accept incoming data on the expected port.

## Q35. What is the purpose of the Indexer receiving configuration?

**Answer:**

The receiving configuration enables a Splunk instance to accept incoming Splunk-to-Splunk data.

A commonly used receiving port is TCP 9997.

Example:

```ini
[splunktcp://9997]
disabled = 0
```

The port must also be reachable over the network and permitted by the relevant firewall rules.

# Section 6 – Splunk Ports

## Q36. What are the important default Splunk ports?

**Answer:**

| Port        | Purpose                                 |
| ----------- | --------------------------------------- |
| TCP 8000    | Splunk Web.                             |
| TCP 8089    | Splunk management port and REST API.    |
| TCP 9997    | Common Splunk-to-Splunk receiving port. |
| TCP 8088    | HTTP Event Collector.                   |
| UDP/TCP 514 | Common Syslog port.                     |
| TCP 6514    | Common Syslog over TLS port.            |

These are default or commonly used port assignments. Administrators can change them.

## Q37. What is port 8000 used for?

**Answer:**

TCP port 8000 is the default port used by Splunk Web.

Users access the Splunk browser interface through this port.

Example:

```text
http://<splunk-server-ip>:8000
```

## Q38. What is port 8089 used for?

**Answer:**

TCP port 8089 is the default Splunk management port.

It is commonly used for:

- Splunk management communication.
- REST API access.
- Certain internal management operations.

It is not the normal Splunk Web interface port.

## Q39. What is port 9997 used for?

**Answer:**

TCP port 9997 is commonly used for Splunk-to-Splunk data forwarding.

For example, a Universal Forwarder can send collected data to an Indexer listening on port 9997.

## Q40. What is port 8088 used for?

**Answer:**

TCP port 8088 is the default port commonly used by HTTP Event Collector.

Applications and supported clients can send event data to Splunk through HEC.

# Section 7 – Splunk Metadata

## Q41. What is the difference between host, source, sourcetype, and index?

**Answer:**

These are important metadata fields associated with Splunk events.

| Field        | Meaning                                | Example             |
| ------------ | -------------------------------------- | ------------------- |
| `host`       | Host associated with the event.        | `server01`          |
| `source`     | Source of the data, often a file path. | `/var/log/auth.log` |
| `sourcetype` | Type or format of data.                | `linux_secure`      |
| `index`      | Logical storage location of the event. | `linux_auth`        |

Easy way to remember:

- Host = Which machine?
- Source = Which file or input?
- Sourcetype = What kind of data?
- Index = Where is the event stored?

## Q42. What does the host field identify?

**Answer:**

The `host` field identifies the host associated with an event.

Example:

```text
host=server01
```

The value may be a hostname, IP address, or another configured identifier.

## Q43. What does the source field identify?

**Answer:**

The `source` field identifies the source of the data.

For file-based inputs, it commonly contains the path of the monitored file.

Example:

```text
source=/var/log/auth.log
```

## Q44. What does the sourcetype field identify?

**Answer:**

The `sourcetype` field identifies the type or format of the data.

It helps Splunk interpret events and apply appropriate event processing.

Examples:

```text
linux_secure
syslog
access_combined
```

The actual sourcetype depends on the data source and configuration.

## Q45. What does the index field identify?

**Answer:**

The `index` field identifies the logical storage location where an event is stored.

Example:

```text
index=linux_auth
```

Searching this index retrieves matching events stored in that logical location, subject to permissions and the selected time range.

# Section 8 – SOC and Operational Monitoring

## Q46. What is the difference between NOC and SOC?

**Answer:**

NOC stands for Network Operations Center.

SOC stands for Security Operations Center.

| NOC                                                 | SOC                                                           |
| --------------------------------------------------- | ------------------------------------------------------------- |
| Focuses on network and infrastructure availability. | Focuses on security monitoring and threat detection.          |
| Investigates connectivity and performance issues.   | Investigates suspicious and potentially malicious activities. |
| Handles operational incidents.                      | Handles security incidents.                                   |
| Example: Router interface is down.                  | Example: Suspicious administrative access to a router.        |

Some organizations maintain separate teams, while others have teams with overlapping responsibilities.

## Q47. Can Splunk be used for both operational and security monitoring?

**Answer:**

Yes.

Splunk can analyze data for both operational and security purposes.

Operational monitoring examples:

- Server availability.
- Application errors.
- Network connectivity.
- Disk utilization.
- Service failures.

Security monitoring examples:

- Failed authentication attempts.
- Suspicious logins.
- Unknown administrative access.
- Firewall-denied traffic.
- Unexpected configuration changes.
- Malware alerts.

The objective of the investigation determines whether the activity is operational or security-related.

## Q48. How would you monitor a Wireless Access Point using Splunk?

**Answer:**

A Wireless Access Point (WAP) can produce operational and security-related events.

For operational monitoring, I would examine:

- Device availability.
- Interface status.
- Upstream connectivity.
- Power or hardware alerts.
- Connection failures.

For security monitoring, I would examine:

- Repeated authentication failures.
- Unknown administrative logins.
- Unknown wireless clients.
- Unexpected configuration changes.
- Suspicious traffic patterns.

I would correlate related events and identify whether multiple alerts share a common cause.

## Q49. Can one technical issue generate multiple alerts?

**Answer:**

Yes.

A single root cause can generate multiple alerts across different systems.

For example, an upstream network outage may cause multiple downstream devices and applications to report connectivity failures.

I would correlate timestamps, affected systems, and related events before treating each alert as an independent incident.

# Section 9 – Troubleshooting Scenarios

## Q50. A Linux server is generating logs, but no events are appearing in Splunk. How would you troubleshoot?

**Answer:**

I would troubleshoot the complete data flow systematically.

### Step 1 – Verify the source log

Check whether the expected log file exists and is receiving new entries.

Example:

```bash
sudo tail -f /var/log/auth.log
```

### Step 2 – Check the Forwarder service

```bash
sudo /opt/splunkforwarder/bin/splunk status
```

Confirm that the Universal Forwarder is running.

### Step 3 – Verify input configuration

```bash
sudo /opt/splunkforwarder/bin/splunk btool inputs list --debug
```

Check the monitored file path, input status, index, and sourcetype.

### Step 4 – Verify output configuration

```bash
sudo /opt/splunkforwarder/bin/splunk btool outputs list --debug
```

Confirm that the correct receiving server and port are configured.

### Step 5 – Check forwarding connections

```bash
sudo /opt/splunkforwarder/bin/splunk list forward-server
```

Review the configured forwarding destinations and their connection status.

### Step 6 – Test network connectivity

```bash
nc -vz <indexer-ip> 9997
```

Check whether the Forwarder can establish a TCP connection to the receiving server.

### Step 7 – Verify the receiving port

Confirm that the Indexer is configured to receive data on the expected port and that the port is reachable.

### Step 8 – Check the index and time range

Search the expected index and verify the selected time range.

### Step 9 – Check internal logs

```spl
index=_internal error
```

Review relevant internal errors or warnings.

I would identify the failed layer before making any configuration changes.

## Q51. The Forwarder is running, but no data is reaching the Indexer. What would you check?

**Answer:**

I would check:

1. Whether the input is configured correctly.
2. Whether the monitored file exists.
3. Whether the Forwarder can read the file.
4. Whether `outputs.conf` contains the correct receiving destination.
5. Whether the receiving port is enabled on the Indexer.
6. Whether network connectivity is working.
7. Whether a firewall is blocking the connection.
8. Whether Forwarder logs contain errors.

A running Forwarder does not automatically guarantee that data is being collected and delivered successfully.

## Q52. The Forwarder can connect to the Indexer, but events are not visible in search. What could be the reason?

**Answer:**

Possible reasons include:

- Events are being sent to a different index.
- The selected time range is incorrect.
- The wrong sourcetype or search criteria are being used.
- The user does not have permission to search the index.
- Data is not being processed or indexed as expected.
- Events have unexpected timestamps.
- There is a parsing or routing issue.

I would verify the expected index, time range, permissions, and relevant ingestion information before concluding that data is missing.

## Q53. What would you check if the Forwarder cannot connect to the Indexer?

**Answer:**

I would check:

1. Whether the Indexer is running.
2. Whether the receiving port is enabled.
3. Whether the configured Indexer IP address is correct.
4. Whether the configured port is correct.
5. Whether the Forwarder can reach the Indexer.
6. Whether firewalls are blocking the connection.
7. Whether routing is correct.
8. Whether the Forwarder output configuration is correct.

A basic connectivity test is:

```bash
nc -vz <indexer-ip> 9997
```

## Q54. How would you investigate repeated failed SSH login attempts?

**Answer:**

I would first identify the authentication log source and verify that it is being collected in Splunk.

I would investigate:

- Source IP address.
- Target hostname.
- Username.
- Number of failed attempts.
- Timestamps.
- Whether any successful login followed the failures.
- Whether the source IP is expected.
- Whether similar activity occurred on other servers.

Repeated failed logins may indicate a brute-force attempt, password spraying, misconfiguration, or legitimate user error.

I would not classify the activity as malicious based only on the presence of failed logins.

## Q55. What would you do if Splunk Web is not opening?

**Answer:**

I would troubleshoot the Splunk Web service and connectivity.

Checks include:

1. Verify that the Splunk service is running.
2. Confirm the Splunk Web port configuration.
3. Check whether the server is listening on the expected port.
4. Verify network connectivity to the Splunk server.
5. Check host firewall rules.
6. Review Splunk internal logs for errors.

On a typical Linux Splunk Enterprise installation:

```bash
sudo /opt/splunk/bin/splunk status
```

Check listening ports:

```bash
sudo ss -lntp | grep 8000
```

The default Splunk Web port is TCP 8000, unless it has been changed.

## Q56. What is the purpose of Splunk internal logs during troubleshooting?

**Answer:**

Splunk internal logs provide information about Splunk's own processes and activities.

They can help investigate:

- Service errors.
- Forwarding issues.
- Data ingestion problems.
- Search-related activity.
- Splunk Web activity.
- Management API activity.

The common internal index is:

```text
_internal
```

Example search:

```spl
index=_internal error
```

The results should be examined in context because not every warning or error necessarily indicates a critical failure.

# Section 10 – Scenario-Based Interview Questions

## Q57. A firewall is sending Syslog messages to a Syslog server, but Splunk is not showing the firewall logs. What would you investigate?

**Answer:**

I would check the complete collection path.

1. Confirm that the firewall is configured to send Syslog to the correct destination.
2. Verify that the Syslog server is receiving messages.
3. Check the protocol and port being used.
4. Confirm that the Syslog server is configured to forward messages to Splunk.
5. Verify that Splunk is receiving the forwarded data.
6. Check the expected index and sourcetype.
7. Verify the search time range and permissions.
8. Review relevant errors and logs.

I would first determine whether the issue exists between the firewall and Syslog server or between the Syslog server and Splunk.

## Q58. A server is showing multiple alerts for connectivity failures. How would you investigate?

**Answer:**

I would first establish the timeline and scope of the issue.

I would check:

- When the first alert occurred.
- Which systems are affected.
- Whether the alerts share a common source or destination.
- Whether upstream network devices show failures.
- Whether there was a recent configuration or maintenance change.
- Whether other systems experienced the same issue.

I would look for a common root cause rather than assuming every alert represents an independent incident.

## Q59. An event is visible in Splunk, but the source IP field is not available. What could be the reason?

**Answer:**

Possible reasons include:

- The source IP is not present in the raw event.
- The field has not been extracted.
- The field has a different name.
- The selected sourcetype does not provide the expected field extraction.
- The event format is different from what was expected.

I would inspect the raw event, identify the source IP value, and determine whether an existing field extraction or another extraction method is required.

## Q60. An organization wants to collect logs from 200 Linux servers. What approach could be used?

**Answer:**

A common approach is to install and configure a Universal Forwarder on each Linux server.

The Forwarders can:

1. Monitor required log files.
2. Use consistent input configurations.
3. Assign suitable indexes and sourcetypes.
4. Send data to designated receiving Indexers.

A Deployment Server can help centrally distribute supported Forwarder configurations.

The exact architecture depends on the organization's scale, network design, availability requirements, and security policies.

# Final Interview Preparation Advice

Do not memorize these answers word for word.

For every technical question, try to explain:

1. What the component or concept is.
2. Why it is used.
3. How it works.
4. A practical example.

For scenario-based questions, explain your investigation step by step.

For example, when asked why events are missing from Splunk, do not immediately say that the Forwarder is down. Explain how you would verify the source logs, Forwarder service, input configuration, output configuration, network connection, receiving port, indexing, time range, and permissions.

**Interview principle:**

Understand the concept → Explain it clearly → Give a practical example → Describe how you would troubleshoot it.
