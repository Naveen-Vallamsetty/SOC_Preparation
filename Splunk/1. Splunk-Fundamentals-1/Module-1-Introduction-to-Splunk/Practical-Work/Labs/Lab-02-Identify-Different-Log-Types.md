## 5. Lab Tasks

### Task 1 - Identify Linux Log Files

Linux systems generate logs related to authentication, operating system activities, services, kernel events, and package management.

**Step 1: Open the Ubuntu terminal.**

**Step 2: Check the hostname.**

```bash
hostname
```

Expected output:

```text
ubuntu
```

Your actual hostname may be different.

**Step 3: List available log files.**

```bash
ls -lh /var/log/
```

Observe the available files and directories.

**Step 4: Check the authentication log.**

```bash
sudo tail -n 20 /var/log/auth.log
```

Look for events related to:

- SSH authentication.
- Successful login attempts.
- Failed login attempts.
- User and privilege-related activities.

**Step 5: Check the system log.**

```bash
sudo tail -n 20 /var/log/syslog
```

Look for messages related to:

- System services.
- Network services.
- Application activity.
- System warnings and errors.

**Step 6: Check kernel logs if available.**

```bash
sudo tail -n 20 /var/log/kern.log
```

If the file does not exist, record it as unavailable.

**Step 7: Check package management logs.**

```bash
sudo tail -n 20 /var/log/dpkg.log
```

Look for package installation, removal, or upgrade activities.

**Step 8: Check systemd journal.**

```bash
sudo journalctl -n 20
```

This displays recent system journal entries.

**Expected observation:**

You should see log records containing timestamps, process or service names, and event messages.

The exact records depend on your Ubuntu version, installed services, and system activity.

**Record your observations:**

| Log File            | Available? | What type of information did you observe? |
| ------------------- | ---------- | ----------------------------------------- |
| `/var/log/auth.log` |            |                                           |
| `/var/log/syslog`   |            |                                           |
| `/var/log/kern.log` |            |                                           |
| `/var/log/dpkg.log` |            |                                           |
| systemd journal     |            |                                           |

### Task 2 - Identify Windows Event Logs

Windows uses Event Viewer to record operating system, application, and security activities.

Common Windows log categories include:

| Log Category     | Purpose                                     |
| ---------------- | ------------------------------------------- |
| Application      | Application-related events                  |
| Security         | Authentication and security auditing events |
| System           | Operating system and service events         |
| Setup            | Installation and update events              |
| Forwarded Events | Events forwarded from other systems         |

**Step 1: Start your Windows VM if available.**

**Step 2: Open Event Viewer.**

Press:

```text
Windows + R
```

Enter:

```text
eventvwr.msc
```

Press Enter.

**Step 3: Navigate to:**

```text
Event Viewer
  └── Windows Logs
      ├── Application
      ├── Security
      ├── Setup
      └── System
```

**Step 4: Open the Security log.**

Observe the available events.

Look for:

- Event ID.
- Date and time.
- Source.
- Event level.
- Event description.

**Step 5: If available, inspect a successful or failed logon event.**

Common Windows Security Event IDs include:

| Event ID | Description                      |
| -------- | -------------------------------- |
| 4624     | Successful logon                 |
| 4625     | Failed logon                     |
| 4634     | Account logoff                   |
| 4648     | Logon using explicit credentials |
| 4720     | User account created             |
| 4726     | User account deleted             |
| 4740     | User account locked out          |

**Expected observation:**

Windows Event Viewer displays structured event records containing event identifiers, timestamps, sources, and descriptions.

**If Windows VM is unavailable:**

You can skip the hands-on Windows portion. Use the event examples and reference table to understand the format. Do not record sample events as events observed on your own Windows system.

**Record your observations:**

| Event description              |             |

### Task 3 - Identify Network Device Logs

Network devices such as firewalls, routers, and switches generate logs about network traffic, connectivity, authentication, and configuration changes.

Review the following sample records.

**Firewall log example:**

```text
2026-11-19 10:20:15 ALLOW TCP 192.168.1.25 192.168.1.100 51520 443
```

Identify:

| Field            | Value               |
| ---------------- | ------------------- |
| Timestamp        | 2026-11-19 10:20:15 |
| Action           | ALLOW               |
| Protocol         | TCP                 |
| Source IP        | 192.168.1.25        |
| Destination IP   | 192.168.1.100       |
| Source Port      | 51520               |
| Destination Port | 443                 |

**Router log example:**

```text
Nov 19 10:25:10 router01 %LINK-3-UPDOWN: Interface GigabitEthernet0/1 changed state to down
```

Identify:

| Field     | Value                   |
| --------- | ----------------------- |
| Hostname  | router01                |
| Event     | Interface state changed |
| Interface | GigabitEthernet0/1      |
| New State | Down                    |

**Your activity:**

1. Identify the source device in each example.
2. Identify the event being recorded.
3. Identify the information that could help an analyst investigate the event.
4. Record your observations.

**Expected observation:**

Firewall logs provide information about network connections and traffic decisions.

Router and switch logs provide information about network interfaces, connectivity, and device operations.

### Task 4 - Identify Wireless Access Point Logs

Wireless access points generate logs about wireless clients, authentication, connections, and configuration changes.

Review this sample record:

```text
Nov 19 10:30:12 AP01: Authentication failed for client MAC 00:11:22:33:44:55
```

Identify:

| Field      | Value                  |
| ---------- | ---------------------- |
| Device     | AP01                   |
| Event      | Authentication failure |
| Client MAC | 00:11:22:33:44:55      |

Common WAP events include:

- Wireless client connected.
- Wireless client disconnected.
- Authentication failure.
- Unknown device attempted to connect.
- Access point restarted.
- Wireless configuration changed.

**Your activity:**

Review the sample record and identify:

1. Which device generated the event?
2. What happened?
3. Which client was involved?
4. What additional information would you need to investigate the event?

**Expected observation:**

WAP logs can help monitor wireless connectivity and identify unusual authentication or configuration activities.

A MAC address alone does not prove the identity of a person or device.

### Task 5 - Identify VPN Logs

VPN gateways generate logs related to remote access, authentication, and VPN sessions.

Review this sample record:

```text
Nov 19 10:35:22 vpn-gateway: Login failed for user testuser from 203.0.113.25
```

Identify:

| Field     | Value         |
| --------- | ------------- |
| Device    | vpn-gateway   |
| Event     | Login failure |
| Username  | testuser      |
| Source IP | 203.0.113.25  |

The IP address `203.0.113.25` is reserved for documentation and is used here only as an example.

Common VPN events include:

- Login successful.
- Login failed.
- VPN session established.
- VPN session disconnected.
- Internal IP address assigned.
- Configuration changed.

**Your activity:**

1. Identify the VPN gateway.
2. Identify the username.
3. Identify the source IP.
4. Identify the authentication result.
5. Consider what additional events would help determine whether the activity is suspicious.

**Expected observation:**

VPN logs help monitor remote access and investigate authentication failures, unusual sessions, and potentially suspicious access.

### Task 6 - Identify Web Server Logs

Web servers record HTTP requests received from clients.

Review this sample Apache access log:

```text
192.0.2.25 - - [19/Nov/2026:10:40:15 +0000] "GET /login HTTP/1.1" 200 1250
```

Identify:

| Field              | Value                |
| ------------------ | -------------------- |
| Client IP          | 192.0.2.25           |
| Timestamp          | 19/Nov/2026:10:40:15 |
| HTTP Method        | GET                  |
| Requested Resource | /login               |
| HTTP Version       | HTTP/1.1             |
| Response Code      | 200                  |
| Response Size      | 1250 bytes           |

The IP address `192.0.2.25` is reserved for documentation and is used here only as an example.

Common HTTP response codes:

| Status Code | Meaning               |
| ----------- | --------------------- |
| 200         | OK                    |
| 301         | Moved Permanently     |
| 302         | Found / Redirect      |
| 400         | Bad Request           |
| 401         | Unauthorized          |
| 403         | Forbidden             |
| 404         | Not Found             |
| 500         | Internal Server Error |
| 502         | Bad Gateway           |
| 503         | Service Unavailable   |

**Your activity:**

1. Identify the client IP.
2. Identify the requested resource.
3. Identify the HTTP method.
4. Identify the response status.
5. Determine what additional requests or events would help investigate suspicious web activity.

**Expected observation:**

Web server logs provide information about client requests, requested resources, timestamps, and server responses.

### Task 7 - Identify Application Logs

Applications generate logs about their internal operations and user activities.

Review this sample record:

```text
2026-11-19 10:45:20 ERROR AuthenticationService - Login failed for user testuser
```

Identify:

| Field     | Value                          |
| --------- | ------------------------------ |
| Timestamp | 2026-11-19 10:45:20            |
| Severity  | ERROR                          |
| Component | AuthenticationService          |
| Message   | Login failed for user testuser |

Common application events include:

- Application startup and shutdown.
- Authentication success and failure.
- Database connection failures.
- API requests.
- Application exceptions.
- Permission errors.

**Your activity:**

Identify the timestamp, severity, application component, and event message.

**Expected observation:**

Application logs help analysts understand application behavior, authentication activity, errors, and possible misuse of application functionality.

### Task 8 - Explore Splunk Internal Logs

Splunk generates its own internal logs.

These logs provide information about Splunk services, searches, data ingestion, access activity, and platform operations.

**Step 1: Open Splunk Web.**

Navigate to:

```text
Apps → Search & Reporting
```

**Step 2: Search all available internal events.**

```spl
index=_internal
```

**Step 3: Inspect the returned events.**

Select an event and observe:

- `_time`
- `host`
- `source`
- `sourcetype`
- `_raw`

**Step 4: Search Splunk service logs.**

```spl
index=_internal sourcetype=splunkd
```

**Step 5: Search Splunk management access logs.**

```spl
index=_internal sourcetype=splunkd_access
```

**Step 6: Search Splunk Web access logs.**

```spl
index=_internal sourcetype=splunkd_ui_access
```

**Step 7: Review the available events.**

Record which sourcetypes return events in your environment.

**Expected observation:**

You should be able to identify different categories of Splunk internal events.

Not every sourcetype is guaranteed to contain events in every environment.

**Record your observations:**

| Search                                         | Events Returned? | Observation |
| ---------------------------------------------- | ---------------- | ----------- |

| `index=_internal sourcetype=splunkd`           |                  |             |
| `index=_internal sourcetype=splunkd_access`    |                  |             |

## 7. Troubleshooting

### Issue 1 - Authentication log does not exist

Possible reasons:

- Different Linux logging configuration.
- Authentication messages are stored in systemd journal.
- The distribution uses different log locations.

Try:

```bash
sudo journalctl -u ssh -n 30
```

### Issue 2 - Permission denied while reading logs

Some Linux log files require administrator privileges.

Use:

```bash
sudo tail -n 20 /var/log/auth.log
```

### Issue 3 - Windows Event Viewer is unavailable

If your Windows VM is not installed or running, skip the practical inspection and use the sample event records.

### Issue 4 - No events appear in Splunk

Check whether Splunk is running:

```bash
sudo /opt/splunk/bin/splunk status
```

Then search:

```spl
index=_internal
```

Also verify:

- Selected time range.
- Index name.
- User permissions.
- Whether Splunk is generating internal events.

### Issue 5 - A particular log file is missing

Not all Linux distributions use the same log files.

Record the file as unavailable and inspect the system journal or an equivalent log source instead.
